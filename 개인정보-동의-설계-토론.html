작성일 2026-06-24 · 상태: 설계 합의안 (실제 개발은 추가 토의 후 적용)
⚠️ 본 문서는 한국 개인정보보호법(PIPA) 구조에 근거한 설계 관점 정리이며 법률 자문이 아닙니다. 실제 서비스 런칭 전 개인정보 전문 변호사 검토를 권장합니다.

0결정 요약

  • 병원/의사(의료) 상담 → 상담 텍스트 저장하지 않음 (현 상태 유지). 건강정보=민감정보(§23) 트랙 회피.
  • 그 외 전문가 상담 → 상담 내용·연락처를 매칭된 전문가에게 제공.
  • 전문가는 독립 사업자 → 법적 성격은 제3자 제공(§17) (위탁 아님).
  • 마케팅 활용 동의 → 지금 받아만 두고 실제 발송은 추후. (선택 동의)

1핵심 쟁점: 용어의 함정

"상담 내용을 전문가가 보게 한다"는 것은 마케팅 활용 동의가 아니라 제3자 제공 동의입니다. 이를 혼동하면 정작 필요한 동의(제공)는 빠지고, 불필요한 동의(마케팅)만 받는 엇박자가 발생합니다.

하려는 것실제 법적 성격근거
상담 내용·전화번호를 전문가가 열람하도록 제공제3자 제공PIPA §17
이후 사용자에게 광고·홍보 발송마케팅 활용 동의 (선택)PIPA §22

2제공받는 자 특정 문제 → 2단계 동의

§17은 원칙적으로 '제공받는 자'를 특정해야 하나, 가입 시점엔 어느 전문가에게 갈지 모름. 따라서 2단계로 해결:

  • 가입 시 (포괄): "상담 요청 시 매칭된 해당 분야 전문가에게 제공" — 4요소 고지 후 동의.
  • 상담 전송 직전 (특정): "○○세무사(사업자번호 …)에게 전달됩니다" just-in-time 고지 + 확인.
각 상담 전송 = 하나의 '제공 이벤트'. 따라서 제공 내역을 로그로 남기는 것이 §17 약점을 보완하는 핵심.

3가입 폼 동의 구조

구분항목고지 내용
필수이용약관 동의—
필수개인정보 수집·이용항목: 이름·휴대전화번호·상담요청 내용 / 목적: 전문가 상담 매칭·응대 / 기간: 탈퇴 시까지(상담내용은 종료 후 N일)
필수개인정보 제3자 제공제공받는 자: 요청 분야 입점 전문가 / 항목: 이름·전화번호·상담내용 / 목적: 상담 응대 / 기간: 종료 후 N일 후 파기
선택마케팅 활용 동의거부해도 서비스 이용 가능
제3자 제공을 '필수'로 두는 근거: 전문가가 안 보면 상담 자체가 불가 → 서비스 본질. 단 반드시 별도 체크박스로 분리(묶음 동의 금지).

4동의 이력 + 제공 내역 스키마 (초안)

"누가·언제·어떤 버전에 동의했는지"와 "언제·누구에게 제공했는지"를 입증 가능해야 함.

-- 동의 이력 (버전 관리)
create table consent_log (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id),
  type        text not null,         -- 'terms'|'privacy'|'third_party'|'marketing'
  version     text not null,         -- 약관 버전 (예: '2026-06-24')
  agreed      boolean not null,
  agreed_at   timestamptz not null default now(),
  ip          inet,
  user_agent  text
);

-- 제공 내역 (상담 전송 = 제공 이벤트)
create table provision_log (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references auth.users(id),
  expert_id       uuid not null references experts(id),
  items           text[] not null default '{name,phone,content}',
  purpose         text not null default '상담 응대',
  provided_at     timestamptz not null default now(),
  retention_until timestamptz not null   -- 상담 종료 후 N일
);

5RLS: 전문가는 매칭된 건·기간 내만

alter table consultations enable row level security;

-- 본인 상담만
create policy own_read on consultations
  for select using (auth.uid() = user_id);

-- 매칭된 전문가가 보유기간 내 조회
create policy expert_read on consultations
  for select using (
    exists (
      select 1 from provision_log p
      where p.user_id = consultations.user_id
        and p.expert_id = auth.uid()
        and now() < p.retention_until
    )
  );

6보호조치 체크리스트

  • 암호화: 전화번호·상담 텍스트 저장 시 암호화.
  • 접근통제·감사로그: Supabase RLS + 누가 열람했는지 기록.
  • 보유기간·파기: 상담 종료 후 N일 경과 시 자동 파기/분리보관.
  • 가명/통계 처리: 분석·개선 용도는 원문 대신 가명데이터로.
  • 개인정보처리방침 게시 의무.
  • 의료 분리 서버단 강제: UI 분기만으론 우회 가능 → 저장 직전 서버 코드에서도 의료 상담 텍스트 비저장을 강제.
✅ 코드 조사 완료 (2026-06-25) — 현재 requests/likes/consultations에 INSERT하는 코드가 한 곳도 없음. 즉 상담을 전문가에게 전송하는 기능 자체가 아직 미구현. "잘못 저장 중인 걸 고치는" 상황이 아니라, 전송 기능을 만들기 전에 개인정보 뼈대를 먼저 세우는 깨끗한 출발점.

7적용 설계안 (1/3): 범위 · 핵심 원칙 · 데이터 모델

문서 위치(예정): docs/02-design/features/privacy-consent.design.md (CLAUDE.md의 design-docs 컨벤션 준수)

범위: 이번엔 설계서만 확정. 코드 변경 없음. 실제 구현은 "전문가 연결(전송) 기능" 개발 시 이 스펙을 따른다.

핵심 원칙 (확정된 결정)

  1. 의료(MED)는 상담 텍스트 비저장 — 건강정보=민감정보(§23) 트랙 회피
  2. 그 외 분야는 매칭된 전문가에게 제공 — 법적 성격 = 제3자 제공(§17), 위탁 아님
  3. 저장 항목은 최소화: 이름·전화번호·요청내용만
  4. 보유기간 90일 (상담 종료 후 90일 이내 파기)
  5. 제공 시점 = 2개 포인트: ① 전화버튼 클릭  ② 상담요청 버튼 클릭(미구현)
  6. 동의 = 최초 로그인 직후 1회 (4종)

데이터 모델 (requests로 통일)

테이블역할비고
requests 기존 재사용 상담 본체. 항목: 이름·전화·query(요청내용)·vertical·urgency 의료 분리: vertical='MED'면 query 비저장 + DB CHECK 제약 + 서버 코드 이중 강제
consent_log 신규 동의 이력 (누가·언제·어떤 버전 동의) §4 스키마 초안 기준
provision_log 신규 제공 내역 (언제·누구에게 제공, retention_until) 제공 이벤트 2포인트에서 기록
consultations 폐기 — requests로 통일하여 스키마 중복 제거
현재 requests에는 name·phone 컬럼이 없음(query·session_id만 존재). → 이름·전화 컬럼 추가 필요 (구현 시 마이그레이션).
